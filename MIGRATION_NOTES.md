# Rodel's Catering migration

## Evidence and scope

After the initial briefs, the user identified `C:\xampp\htdocs\RodelWeb`. A read-only scan of **all 181 non-vendor files (137 PHP)** excluded vendor and PHPMailer internals. Core public terms, reservation/menu/setup handlers, cancellation/refund/reschedule handlers and authorization were inspected directly. All 181 file hashes were verified unchanged during the initial rebuild. No SQL dump or stored procedure definitions exist. No legacy files were changed. The machine-specific scan helpers/inventory were subsequently removed at the user's request during hosting cleanup. Original Logo.png, Example1.jpg, Wedding2.jpg and Corporate2.jpg are copied into public/images; profile images and all PHP/config/debug files are excluded. The new presentation retains the original gold/ivory identity, original logo and event photos, with a burgundy accent. Catalog seeds remain illustrative because catalog database records are unavailable.

The deployment target is now a hosted Supabase.com project plus a hosted React frontend. Local container configuration, stub seed entry point and downloaded browser/testing tools were removed. All versioned SQL migrations remain; `supabase/setup.sql` combines them for one-time installation through the hosted SQL Editor, including the catalog seed in 0012_seed.sql. A fresh-project preflight and transaction prevent accidental changes to an existing public schema.

## Canonical rules and intentional corrections

- At most three capacity-holding reservations per Manila event date: approved/completed plus previously approved reservations awaiting cancellation review. A database-controlled holds_capacity field preserves the slot only until approved cancellation releases it; later refund requests do not reclaim capacity. Unapproved cancellation requests do not occupy a confirmed slot. Advisory transaction locks plus a trigger serialize approvals and date changes. One active reservation per customer/date is a partial unique index (including drafts).
- Cancellation requires event local midnight to be strictly more than 72 hours from request time. Manager review can approve or reject; rejected requests restore the previous state. An unpaid draft can be withdrawn under the same rule.
- Reschedules require an approved reservation, a future date and no pending checkout. Customer requests; manager approval atomically changes date after capacity/duplicate checks. Three successful reschedules per reservation per Manila calendar month; failures/rejections do not consume the quota. Count is an append-only history rather than a mutable browser counter.
- Only unpaid drafts/pending/for_approval reservations are editable, and no open checkout may exist. Finalizing validates exactly the package dish count plus a drink, dessert, setup, address, tables and enough active chairs. Prices are snapshotted at finalization. Catalog changes do not reprice a finalized booking. Mixed chair types are supported; extra-chair charges apply to total quantity above guests, allocated to the highest-priced chair types first as in the legacy server. Add-ons/features are flat unit prices with explicit quantity for add-ons. New bookings and reschedule targets require three calendar days of lead time; event times remain 07:00–22:00 Manila. Guest minimums are package-configured rather than the legacy UI-only fixed 100.
- Pending checkout freezes edits, cancellation and rescheduling until verified confirmation or explicit provider reconciliation. A 24-hour local retry deadline does not claim the provider has expired; stale/ambiguous checkouts require an operator to verify/expire provider state before marking the local attempt failed. The Edge Function refuses unsafe retries after an ambiguous provider error.
- Payment approval only follows authenticated provider processing. If capacity is exhausted, payment is recorded and the reservation remains for_approval for operational review; the customer gets a notice. Success redirect never writes a payment.
- Partial payment requires exactly 50% of the total; full pays the entire unpaid total; balance pays the remainder after a down payment. A payment cannot exceed the remaining balance.
- Refund eligibility is calculated once at request time after approved cancellation: 30% of paid amount for an exact 50% down payment, 70% of paid amount when fully paid. Other partial amounts are rejected for manual investigation. Rates live in app_settings. Manager approval cannot override the frozen amount. Refund completion requires a PayMongo refund processed server-side, never a browser checkbox.
- Roles come from profiles in the database. Registration metadata cannot assign roles. Super admins may assign customer/manager only; super-admin bootstrap is a restricted database operator action. Staff cannot demote themselves through this workflow.
- Maintenance blocks customer writes in database helpers and public/customer pages; super-admin sign-in/settings bypass remains available. RLS hides public catalog during maintenance. Managers can inspect operational records but cannot originate customer operations.
- Audit entries derive actors from auth.uid(); webhook actors are null and carry provider IDs. Audit logs have no client write policies. Notifications are generated in database transactions.
- Browser SQL recovery, redirect-confirmed payments, custom password/OTP code, arbitrary status strings, hard-coded secret values, browser chatbot provider calls, inconsistent refund math, and role-by-session-only authorization are deliberately removed.

## Later import and remaining source comparison

The legacy public terms mention 5% weekly overdue charges but the supplied behavior has no reliable canonical due-date/late-fee ledger. This rebuild intentionally does not assess automated penalties or retroactive fees; outstanding balances contain only the confirmed catering quote. Establish a reviewed due-date and fee policy before adding such charges. The original menu category/package database content is absent; seeded names/prices/minimums are examples to be replaced by the business.

Obtain a protected MySQL export. Rotate compromised legacy credentials independently. Import through a separate staged transform; add legacy_id columns before import, preserve source IDs, map roles/statuses explicitly, reconcile paid/refunded totals and timezone conversion, and link customers through an invitation/account-claim process. Never fabricate historical reservations or plaintext passwords. Back up both systems before cutover and reconcile totals before switching traffic. The public legacy wording says three reschedules total while reschedule_submit.php enforces three per month; this rebuild intentionally preserves implemented monthly behavior with manager review. The legacy new-date minimum is three days ahead; the new system retains that lead time. Legacy refund completion deletes the reservation; the rebuild preserves financial and reservation records permanently. The legacy server omits additional_chair_quantities while its UI displays them; the rebuild includes all selected chair quantities in canonical pricing.
