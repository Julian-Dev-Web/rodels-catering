# Upcoming-event reminder email setup

Status checked October 15, 2026: the hosted five-minute scheduler, secure dispatcher and in-app reminders are installed. The configured reminder window is D-7 through D-1 at 07:00 Asia/Manila. Resend credentials and a verified business sender are not configured. The worker correctly reports `email: not_configured`; no real email delivery is claimed. The owner requested these instructions because no business domain is available yet.

1. Obtain a domain controlled by the business and access to its DNS settings. A personal Gmail/Yahoo address or the shared `vercel.app` hosting domain is not a business-owned sending domain. Resend requires a domain you own and verify. A sending subdomain can be used. See [Resend verified domains](https://resend.com/docs/dashboard/domains/introduction).
2. Create a Resend account. Add that domain/subdomain under Domains and install the exact DNS records Resend supplies. Wait until Resend reports it verified. Choose a real sender address on that verified domain; do not invent or use an unverified sender.
3. Create a sending API key, preferably restricted to the verified domain. See [Resend API key permissions](https://resend.com/docs/api-reference/api-keys/create-api-key). Keep the key out of chat, GitHub, screenshots and all `VITE_*` variables.
4. In the Supabase project's Edge Function secrets, privately set `RESEND_API_KEY` and `EMAIL_FROM`. The sender format is `Rodel's Catering Services <your-sender@your-verified-domain>`. Confirm `APP_URL` is `https://rodels-catering.vercel.app`. These names are server configuration, not frontend Vercel variables. See [Supabase environment secrets](https://supabase.com/docs/guides/functions/secrets).
5. The reminder dispatcher already has its own private `REMINDER_WORKER_SECRET`, matching Vault entry and Cron job. Preserve these values; do not copy them into browser code. `EMAIL_WORKER_SECRET` is needed separately only if operating the existing generic transactional-email worker; it is not a substitute for the reminder worker token.
6. In Super Admin → Tax & reminders, confirm reminders are enabled and set the desired Manila send time. In Customer → Settings, explicitly enable reminder emails for the authorized test recipient. In-app and email preferences are separate. Email is off by default.
7. With an authorized test inbox and a controlled approved booking in the D-7 through D-1 window, let the scheduled worker run. Verify a single delivery ledger entry for the reservation/date/email channel, a nonempty provider acceptance ID and the Resend log. Then inspect the inbox/spam folder. Provider acceptance alone does not prove inbox delivery.
8. Repeat the same-day tick and verify no duplicate email. Test opt-out and an approved date change/cancellation. Remove only controlled QA fixtures and restore any changed preferences. Do not send tests to real customers without authorization.

The dispatcher is invoked by a backend schedule, not by the customer browser. Cron ticks every five minutes; the first successful eligible tick at or after the chosen Manila time processes that day's reminders. Delayed executions do not backfill several old daily reminders into an email burst. D-0 delivery is not enabled.

The email ledger records leases, attempts, sanitized failure categories, immutable retry payloads and a stable provider idempotency key. Resend retains idempotency keys for 24 hours; retries are bounded to the same Manila reminder day. A timeout, missing acceptance ID or ambiguous provider error is not marked successful. See [Resend idempotency](https://resend.com/docs/dashboard/emails/idempotency-keys). A cancellation during an already accepted provider request cannot recall that email; the ledger records the in-flight outcome and stops future reminders.

Until sender setup and real inbox acceptance are verified, use the installed in-app reminders and report email as **implemented, pending provider configuration and delivery acceptance**.
